## Executive Summary

EDx-App-V2 is a modern web-based laboratory data platform for controlling ElectraDx XP2 electrochemical biosensor instruments. The system enables USB-connected device control, Lua script execution, real-time data streaming, and comprehensive test management for FDA Class II medical device compliance (21 CFR Part 11, IEC 62304, ISO 14971).

This PRD documents the completed backend infrastructure and defines remaining work for full production deployment.

## 1. Project Overview

### 1.1 Background

ElectraDx develops FDA Class II electrochemical biosensor medical devices (XP2) for glucose and creatinine detection. The current PyQt6 desktop application works but has limitations for multi-device scaling, cloud integration, and modern UI/UX.

EDx-App-V2 replaces the desktop app with a web-based architecture that:
- Maintains full USB hardware control capabilities
- Enables future WiFi/MQTT device communication
- Supports 20-100+ instruments across multiple labs
- Provides real-time data visualization
- Integrates with AWS S3, LabGuru ELN, and future cloud services

### 1.2 Goals

**Primary:**
- ✅ Preserve working USB device communication from legacy app
- ✅ Build FastAPI backend with WebSocket real-time streaming
- 🔄 Create modern React frontend with live data visualization
- 🔄 Implement script library management system
- 🔄 Add multi-device orchestration support

**Secondary:**
- Prepare architecture for WiFi/MQTT transition
- Enable FDA compliance features (audit logs, electronic signatures)
- Integrate with AWS cloud services
- Support LabGuru ELN synchronization

### 1.3 Non-Goals (Out of Scope)

- Complete WiFi/MQTT implementation (Phase 3)
- Full audit log system with electronic signatures (Phase 3)
- Advanced data analysis/ML features (Phase 4)
- Mobile app (Future)

### 2.3 Device Communication Protocol

**Command Format:**
```
!<command_name> [args]
```

**Response Format:**
```
<timestamp>  <subsystem>  <level>  <message>
@<error_code>
```

**Key Commands:**
- `!identify` - Get device info (version, serial number)
- `!gpbuf_clear 0` - Clear general purpose buffer
- `!gpbuf_append 0 <data>` - Append to buffer
- `!script_run_gpbuf 0` - Execute script from buffer
- `!script_cancel` - Stop running script
- `motor.magnet:move({})` - Control magnetic particle capture
- `sensor.ir1:read()` - Read IR temperature sensor
- `pstat.chrono_3RTIA_config({})` - Configure chronoamperometry

**Script Upload Process:**
1. Base64 encode script content
2. Split into 76-character chunks
3. Clear buffer: `!gpbuf_clear 0`
4. Upload chunks: `!gpbuf_append 0 <chunk>`
5. Join lines: `!gpbuf_line_join 0 1`
6. Decode: `!gpbuf_base64_decode 1 0`
7. Execute: `!script_run_gpbuf 0`

## 7. WebSocket Events

### 7.1 Connection

**Endpoint:** `ws://localhost:8000/ws/device/{serial_number}`

**Authentication:** None (local USB connection)

### 7.2 Event Structure

All events follow this structure:
```json
{
  "type": "event-type",
  "serial_number": "XP2-...",
  "timestamp": 53015.2703345,
  "raw": "original device output",
  ...additional fields
}
```

### 7.3 Event Types

#### script-position
**Purpose:** Track current execution line  
**Usage:** Highlight line in script editor

```json
{
  "type": "script-position",
  "line": 4,
  "raw": "1128.006  \tscript-position\tI\tsrc=gpbuf, line=4",
  "serial_number": "XP2-...",
  "timestamp": 53015.5969962
}
```

#### script-output
**Purpose:** Print statements from script  
**Usage:** Append to output console

```json
{
  "type": "script-output",
  "message": "Hello from XP2!",
  "raw": "1128.006  \tscript-output\tI\tHello from XP2!",
  "serial_number": "XP2-...",
  "timestamp": 53015.5975022
}
```

#### script-status
**Purpose:** Script thread status  
**Usage:** Append to log panel

```json
{
  "type": "script-status",
  "message": "Delay for 200ms (200 timer ticks)",
  "raw": "28.376  \tscript  \tI\tDelay for 200ms (200 timer ticks)",
  "serial_number": "XP2-...",
  "timestamp": 53015.5975022
}
```

#### motor-status
**Purpose:** Motor movement updates  
**Usage:** Log panel, status indicators

```json
{
  "type": "motor-status",
  "message": "Stopping motor after motor stop event 0x0001",
  "raw": "1128.866  \tmotor  \tI\tStopping motor...",
  "serial_number": "XP2-...",
  "timestamp": 53016.4765456
}
```

#### data-sample
**Purpose:** Chronoamperometry data point  
**Usage:** Plot on chart

```json
{
  "type": "data-sample",
  "index": 1,
  "value": 12345.67,
  "raw": "Sample[1] = 12345.67",
  "serial_number": "XP2-...",
  "timestamp": 53016.5
}
```

#### temperature
**Purpose:** IR sensor reading  
**Usage:** Update temperature displays

```json
{
  "type": "temperature",
  "sensor": "ir1",
  "value": 37.5,
  "raw": "temp ir1: 37.5",
  "serial_number": "XP2-...",
  "timestamp": 53016.5
}
```

#### log
**Purpose:** General device output  
**Usage:** Debug log panel

```json
{
  "type": "log",
  "message": "SCRIPT_RUN_START",
  "raw": "SCRIPT_RUN_START",
  "serial_number": "XP2-...",
  "timestamp": 53015.3816842
}
```

### 7.4 Frontend WebSocket Handling

**React Hook Example:**
```typescript
useEffect(() => {
  const ws = new WebSocket(`ws://localhost:8000/ws/device/${serialNumber}`);
  
  ws.onmessage = (event) => {
    const data = JSON.parse(event.data);
    
    switch(data.type) {
      case 'script-position':
        setCurrentLine(data.line);
        break;
      case 'script-output':
        appendToConsole(data.message);
        break;
      case 'data-sample':
        addDataPoint(data.index, data.value);
        break;
      case 'temperature':
        updateTemperature(data.sensor, data.value);
        break;
    }
  };
  
  return () => ws.close();
}, [serialNumber]);
```

## 8. Data Models

### 8.1 Device Model

```python
class Device:
    serial_number: str          # e.g., "XP2-203038543232500F0031004F"
    com_port: str              # e.g., "COM35"
    status: Literal["connected", "idle", "running", "error"]
    temperature_ir1: Optional[float]
    temperature_ir2: Optional[float]
    script_running: bool
    last_seen: datetime
    uptime_seconds: int
```

### 8.2 Script Model

```python
class Script:
    id: str                    # UUID
    name: str                  # e.g., "Control Script 1"
    content: str               # Lua script content
    size_bytes: int
    created_at: datetime
    updated_at: datetime
```

class Run:

## 14. Risks and Mitigations

### 14.1 Technical Risks

| Risk | Impact | Probability | Mitigation |
|------|--------|-------------|------------|
| USB connection instability | High | Medium | Auto-reconnect, connection health monitoring |
| WebSocket connection drops | Medium | High | Exponential backoff retry, status banner |
| Script timeout | High | Low | Configurable timeout, stop button |
| Data loss during streaming | High | Low | Ring buffer, data persistence |
| Firmware bugs | Medium | Medium | Error handling, fallback modes |

### 14.2 Compliance Risks

| Risk | Impact | Probability | Mitigation |
|------|--------|-------------|------------|
| FDA audit failure | Critical | Low | Pre-submission review, validation testing |
| Data integrity issues | High | Low | ALCOA+ compliance, audit logs |
| Electronic signature non-compliance | Medium | Low | 21 CFR Part 11 implementation |

### 14.3 Business Risks

| Risk | Impact | Probability | Mitigation |
|------|--------|-------------|------------|
| User resistance to change | Medium | Medium | Training, gradual rollout |
| Performance issues at scale | High | Medium | Load testing, optimization |
| Cloud costs | Medium | Medium | Cost monitoring, resource optimization |
